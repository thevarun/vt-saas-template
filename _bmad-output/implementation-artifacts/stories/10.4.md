# Story 10.4: Vercel AI SDK Chat API

Status: ready-for-dev

## Story

As a template user (developer),
I want a streaming chat API using Vercel AI SDK,
so that I can build chat features with full control over the LLM integration.

## Acceptance Criteria

1. **Given** an authenticated user
   **When** I POST to `/api/chat/vercel` with a message
   **Then** I receive a streaming SSE response
   **And** the response format matches Vercel AI SDK `useChat` expectations

2. **Given** a new conversation
   **When** I send the first message
   **Then** a new conversation record is created in the database
   **And** the message is persisted with role='user'
   **And** the assistant response is persisted with role='assistant'

3. **Given** an existing conversation
   **When** I send a message with `conversationId`
   **Then** messages are appended to the existing conversation
   **And** `updatedAt` timestamp is refreshed

4. **Given** an unauthenticated request
   **When** I POST to `/api/chat/vercel`
   **Then** I receive 401 Unauthorized
   **And** error format matches API conventions

5. **Given** the conversation metadata
   **When** I review stored data
   **Then** `tokenCount` is tracked per message
   **And** `latencyMs` is recorded for assistant responses

6. **Given** the API implementation
   **When** I review the code
   **Then** the OpenAI API key is never exposed to client-side
   **And** all AI provider credentials are server-side only

7. **Given** the streaming response
   **When** I test the API
   **Then** proper SSE headers are set (`text/event-stream`, `Cache-Control: no-cache`)
   **And** the stream ends gracefully
   **And** errors during streaming are handled properly

## Dev Notes

### Architecture Context

This story implements a **streaming chat API** using the Vercel AI SDK as an alternative to the Dify implementation. Key architectural decisions:

1. **API Proxy Pattern**: Same security model as Dify - API key stays server-side
2. **Database Persistence**: Separate tables (`vercel_conversations`, `vercel_messages`) from Dify (`threads`)
3. **Streaming Protocol**: SSE (Server-Sent Events) compatible with Vercel AI SDK's `useChat` hook
4. **Provider Agnostic**: Supports OpenAI, Anthropic via `@ai-sdk/*` packages

**Comparison to Dify API:**

| Aspect | Dify API | Vercel AI SDK API |
|--------|----------|-------------------|
| Route | `/api/chat` | `/api/chat/vercel` |
| SDK | Custom Dify client | Vercel AI SDK |
| Provider | Dify-managed | Direct (OpenAI, Anthropic) |
| Streaming | Manual SSE parsing | Built-in via `streamText` |
| History | Dify-managed | Database-managed |
| Observability | Basic logging | LangFuse (Story 10.5) |

The existing Dify API at `src/app/api/chat/route.ts` demonstrates the same proxy pattern:

### Vercel AI SDK Integration

**Core API: `streamText`**

```typescript
import { streamText } from 'ai';
import { openai } from '@ai-sdk/openai';

const result = streamText({
  model: openai('gpt-4o-mini'),
  messages: [
    { role: 'user', content: userMessage },
  ],
});

return result.toDataStreamResponse();
```

**Key Features:**
- Automatic SSE formatting (compatible with `useChat`)
- Token counting built-in (`usage.totalTokens`)
- Error handling and timeouts
- Multiple provider support (swap `openai` for `anthropic`)

**Response Format:**

The `toDataStreamResponse()` returns SSE chunks like:

```
data: {"type":"text-delta","textDelta":"Hello"}

data: {"type":"text-delta","textDelta":" world"}

data: {"type":"finish","usage":{"totalTokens":15}}
```

This format is auto-consumed by `useChat` hook on the client.

### Security Model

**API Key Protection:**
1. Store keys in `.env.local` (gitignored)
2. Access keys only in API routes (server-side)
3. Never pass keys to client components
4. Validate session before proxying requests

**Conversation Access Control:**
- All database queries use Supabase client with RLS enabled
- Users can only access their own conversations
- Return 404 (not 403) for unauthorized access (security: don't reveal existence)

**Input Validation:**
- Message: required, string, max 10000 chars
- ConversationId: optional, alphanumeric + hyphens, max 128 chars
- Reject malformed requests with 400 + clear error message

import {

**Error Mapping:**

| Scenario | Response | Code |
|----------|----------|------|
| No session | 401 | `unauthorizedError()` |
| Invalid input | 400 | `invalidRequestError(msg)` |
| AI rate limit | 429 | Custom with retry-after |
| AI timeout | 408 | Custom timeout error |
| Database error | 500 | `internalError()` |
| Unknown error | 500 | `internalError()` |

**Logging:**
- Use `logApiError` for all errors
- Add Sentry breadcrumbs for debugging
- Don't expose internal errors to client
- Log API key issues without exposing key

### Streaming Implementation Pattern

**SSE Headers:**

```typescript
return new Response(stream, {
  headers: {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    'Connection': 'keep-alive',
  },
});
```

**With Vercel AI SDK:**

```typescript
const result = streamText({
  model: openai('gpt-4o-mini'),
  messages: conversationHistory,
});

// Automatically sets correct headers and formats as SSE
return result.toDataStreamResponse();
```

**Stream Lifecycle:**
1. Validate request → return 4xx if invalid
2. Start stream → send headers immediately
3. Generate chunks → send as SSE events
4. Track metadata → accumulate for persistence
5. End stream → persist messages asynchronously
6. Handle errors → log, don't crash stream mid-way

### Message Persistence Strategy

**Fire-and-Forget Pattern:**

```typescript
// After stream completes
Promise.resolve().then(async () => {
  try {
    await createMessage(supabase, conversationId, 'assistant', fullText, {
      tokenCount: usage.totalTokens,
      latencyMs: Date.now() - startTime,
    });
    await updateConversation(supabase, conversationId, {
      lastMessagePreview: fullText.slice(0, 100),
    });
  } catch (error) {
    // Log but don't throw - chat already succeeded
    logger.error({ error, conversationId }, 'Message persistence failed');
    Sentry.captureException(error);
  }
});
```

**Why Fire-and-Forget:**
- Stream already sent to client
- Persistence shouldn't block response
- Chat works even if database write fails
- Errors logged to Sentry for visibility

### Token Counting & Latency

**Token Counting:**

```typescript
const result = await streamText({ model, messages });

// Extract usage after stream completes
const { usage } = await result;
const tokenCount = usage?.totalTokens || null;

// Store with message
await createMessage(supabase, conversationId, 'assistant', text, {
  tokenCount,
});
```

**Latency Tracking:**

```typescript
const startTime = Date.now();

// ... streaming happens ...

const latencyMs = Date.now() - startTime;

await createMessage(supabase, conversationId, 'assistant', text, {
  latencyMs,

```

**Purpose:**
- Cost tracking (tokens)
- Performance monitoring (latency)
