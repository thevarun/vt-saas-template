# Story 10.8: Conversation Management API

Status: ready-for-dev

## Story

As a template user (developer),
I want API endpoints to manage conversations,
so that I can list, view, update, and delete my chat history.

## Acceptance Criteria

1. **Given** an authenticated user
   **When** I GET `/api/chat/vercel/conversations`
   **Then** I receive a list of my conversations
   **And** conversations are sorted by `updatedAt` descending

2. **Given** a conversation ID
   **When** I GET `/api/chat/vercel/conversations/[id]`
   **Then** I receive the conversation with all messages
   **And** messages are sorted by `createdAt` ascending

3. **Given** a conversation
   **When** I PATCH `/api/chat/vercel/conversations/[id]` with title
   **Then** the title is updated
   **And** response includes updated conversation

4. **Given** a conversation
   **When** I DELETE `/api/chat/vercel/conversations/[id]`
   **Then** the conversation is deleted
   **And** all associated messages are deleted (cascade)

5. **Given** another user's conversation
   **When** I try to access it
   **Then** I receive 404 Not Found (not 403, for security)

6. **Given** a list request with pagination params
   **When** I GET `/api/chat/vercel/conversations?limit=10&offset=0`
   **Then** I receive up to 10 conversations
   **And** response includes total count

7. **Given** an unauthenticated request
   **When** I call any conversation endpoint
   **Then** I receive 401 Unauthorized

## Dev Notes

### Architecture Context

This story implements REST API endpoints for managing Vercel AI SDK conversations. These endpoints are consumed by the Vercel Chat UI (Story 10.7) and provide CRUD operations for conversation management.

**Key Design Decisions:**

| Decision | Choice | Rationale |
|----------|--------|-----------|
| API Pattern | Follow `/api/threads` pattern | Consistency with existing codebase |
| Pagination | Query params (limit, offset) | Simple, standard approach |
| Security | 404 instead of 403 | Prevent user enumeration |
| Cascade Delete | Database-level | Schema has `onDelete: 'cascade'` |
| Error Handling | Standard helpers | Consistent error responses |

### Database Context

**Tables:**
- `vercel_conversations` - Conversation metadata (id, userId, title, archived, timestamps)
- `vercel_messages` - Messages within conversations (with FK to conversations)

**Schema Features:**
- Foreign key: `vercel_messages.conversationId` → `vercel_conversations.id`
- Cascade delete: `onDelete: 'cascade'` (messages deleted when conversation deleted)
- Indexes: `userId`, `conversationId`, `createdAt` for performance
- RLS: Row-level security ensures users only access their own data

**Existing Query Helpers:**
- `src/libs/queries/vercelConversations.ts`:
  - `getConversationById(supabase, conversationId)` ✓
  - `createConversation(supabase, userId, title)` ✓
  - `updateConversation(supabase, conversationId, updates)` ✓
  - `listUserConversations(supabase, userId, includeArchived?)` ✓
  - `deleteConversation(supabase, conversationId)` ✗ (to be created)
- `src/libs/queries/vercelMessages.ts`:
  - `getConversationMessages(supabase, conversationId, limit?)` ✓
  - `createMessage(...)` ✓ (not used in this story)

### API Endpoint Patterns

**Reference Implementation:** `/api/threads/route.ts` and `/api/threads/[id]/route.ts`

**Pattern to Follow:**

```typescript
import { cookies } from 'next/headers';
import type { NextRequest } from 'next/server';
import { NextResponse } from 'next/server';
import { z } from 'zod';

import {
  dbError,
  formatZodErrors,
  internalError,
  logApiError,
  logDbError,
  notFoundError,
  unauthorizedError,
  validationError,
} from '@/libs/api/errors';
import { createClient } from '@/libs/supabase/server';
import { listUserConversations } from '@/libs/queries/vercelConversations';

export async function GET(): Promise<Response> {
  try {
    // 1. Validate Supabase session
    const cookieStore = await cookies();
    const supabase = createClient(cookieStore);
    const {
      data: { user },
      error: authError,
    } = await supabase.auth.getUser();

    if (authError || !user) {
      return unauthorizedError();
    }

    // 2. Query database - RLS filters by user_id
    const { data, error: dbQueryError } = await listUserConversations(supabase, user.id);

    if (dbQueryError) {
      logDbError('fetch conversations', dbQueryError, {
        endpoint: '/api/chat/vercel/conversations',
        method: 'GET',
        userId: user.id,
      });
      return dbError('Failed to fetch conversations');
    }

    // 3. Return JSON response
    return NextResponse.json({
      conversations: data ?? [],
      count: data?.length ?? 0,
    });
  } catch (error: any) {
    logApiError(error, {
      endpoint: '/api/chat/vercel/conversations',
      method: 'GET',
    });
    return internalError();
  }
}
```

### Pagination Strategy

**Approach:** Client-side pagination (fetch all, slice in API)

**Why:**
- Simple implementation
- Conversation lists are typically small (<100 items)
- Matches existing `/api/threads` pattern
- No need for cursor-based pagination yet

**Query Params:**
- `limit` - Max conversations to return (default: 50, max: 100)
- `offset` - Number of conversations to skip (default: 0)

**Example:**
```
GET /api/chat/vercel/conversations?limit=10&offset=0  # First 10
GET /api/chat/vercel/conversations?limit=10&offset=10 # Next 10
```

**Implementation:**
```typescript
const url = new URL(request.url);
const limit = Math.min(parseInt(url.searchParams.get('limit') || '50'), 100);
const offset = parseInt(url.searchParams.get('offset') || '0');

const { data, error } = await listUserConversations(supabase, user.id);
const paginatedData = data?.slice(offset, offset + limit);
```

### Security Through Obscurity

**Pattern:** Return 404 for unauthorized access, never 403

**Why:**
- Prevents user enumeration attacks
- Attackers can't distinguish "exists but forbidden" vs "doesn't exist"
- Standard security practice

**Implementation:**
```typescript
// When conversation not found OR not owned by user
if (dbUpdateError || !updatedConversation) {
  const errorCode = (dbUpdateError as any)?.code;
  if (errorCode === 'PGRST116' || !updatedConversation) {
    return notFoundError('Conversation');  // 404, not 403
  }
}
```

**RLS Enforcement:**
- Database RLS filters results to current user automatically
- Query returns null if conversation doesn't exist or isn't owned by user
- API interprets null as 404 (ambiguous by design)

### Error Handling Patterns

**Error Helper Functions (from `@/libs/api/errors`):**

| Helper | HTTP Status | Use When |
|--------|-------------|----------|
| `unauthorizedError()` | 401 | No valid session |
| `validationError(errors)` | 400 | Invalid request body/params |
| `notFoundError('Conversation')` | 404 | Resource doesn't exist |
| `dbError(message)` | 500 | Database query failed |
| `internalError()` | 500 | Unexpected error |

**Logging Functions:**

| Function | Use When |
|----------|----------|
| `logApiError(error, context)` | Catch block errors |
| `logDbError(operation, error, context)` | Database errors |

**Example:**
```typescript
if (dbQueryError) {
  logDbError('fetch conversation', dbQueryError, {
    endpoint: `/api/chat/vercel/conversations/${id}`,
    method: 'GET',
    userId: user.id,
    metadata: { conversationId: id },
  });
  return dbError('Failed to fetch conversation');
}
```

### Cascade Delete Behavior

**Database Schema:**
```typescript
// From src/models/Schema.ts
export const vercelMessages = vtSaasSchema.table(
  'vercel_messages',
  {
    conversationId: uuid('conversation_id')
      .notNull()
      .references(() => vercelConversations.id, { onDelete: 'cascade' }),
    // ... other fields
  }
);
```

**Behavior:**
- When conversation is deleted, all messages are deleted automatically
- No explicit message deletion needed in API
- Database handles referential integrity
- Transaction is atomic (all or nothing)

**API Implementation:**
```typescript
// DELETE /api/chat/vercel/conversations/[id]
const { data, error } = await deleteConversation(supabase, id);
// Messages are automatically deleted via cascade
// Just return 204 No Content
return new Response(null, { status: 204 });
```

### Edge Cases to Handle

1. **Invalid UUID Format:**
   - Drizzle will return null
   - Return 404 Not Found

2. **Empty Conversation List:**
   - Return empty array: `{ conversations: [], count: 0 }`

3. **Pagination Out of Range:**
   - Return empty array if offset > total
   - No error needed

4. **Missing Title in PATCH:**
   - Allow empty updates (no-op)
   - Or require at least one field (validation error)

5. **Concurrent Deletes:**
   - Return 404 if already deleted
   - Database handles race conditions

6. **Messages Exist When Deleting:**
   - Cascade delete handles automatically
   - No special handling needed

### Performance Considerations

**Indexes (Already Exist):**
- `idx_vercel_conversations_user_id` - Fast user lookup
- `idx_vercel_conversations_user_archived` - Fast archived filter
- `idx_vercel_messages_conversation_id` - Fast message lookup

**Query Optimization:**
- RLS automatically adds `WHERE user_id = auth.uid()`
- Sorting by `updated_at` uses index
- Pagination happens in-memory (acceptable for small lists)

**Future Optimizations (If Needed):**
- Add database-level pagination (LIMIT/OFFSET in query)
- Add cursor-based pagination for large datasets
- Cache conversation counts
