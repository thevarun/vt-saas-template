## Dev Notes

### Architecture Context

This story focuses on **code quality and maintainability** for the Dify chat implementation. Story 10.1 has already moved the chat to `/chat/dify`, so this story is about cleaning up the existing code.

**Current State (After Story 10.1):**
```
src/app/[locale]/(auth)/chat/dify/
├── page.tsx              # Dify chat page
├── [threadId]/page.tsx   # Thread detail
└── error.tsx             # Error boundary

src/components/chat/
├── ChatInterface.tsx     # Main chat component (Dify-specific adapter)
├── Thread.tsx            # Reusable thread UI
├── ThreadListSidebar.tsx # Dify thread list
├── ThreadItem.tsx        # Thread list item
├── AppShell.tsx          # Layout wrapper
├── TypingIndicator.tsx   # Loading indicator
├── ErrorThreadState.tsx  # Error UI
├── EmptyThreadState.tsx  # Empty state UI
└── ThreadListSkeleton.tsx # Loading skeleton

src/libs/dify/
├── client.ts             # Dify API client
├── config.ts             # Configuration
└── types.ts              # TypeScript types

src/app/api/chat/
├── route.ts              # Dify chat API proxy
└── messages/
    └── route.ts          # Message history API
```

### Key Implementation Notes

1. **No HealthCompanion References**: The codebase has already been cleaned of HealthCompanion references. Verify this is still true and no new ones were added.

2. **Code Quality Standards**:
   - All public functions must have JSDoc comments
   - No unused imports or variables
   - No dead code or commented-out sections
   - Consistent error handling patterns
   - Proper TypeScript types (no `any` unless necessary)

3. **Environment Variable Handling**:
   - Use `Env` utility from `src/libs/Env.ts`
   - Never hardcode API keys or URLs
   - Gracefully handle missing configuration
   - Document all required variables

4. **Error Handling Patterns**:
   - API routes use standard error responses from `@/libs/api/errors`
   - Components use Error Boundaries for rendering errors
   - Client-side errors show user-friendly messages
   - All errors logged appropriately (Sentry for production, console for dev)

5. **SSE Streaming Implementation**:
   - Server-side: Transform Dify stream with proper headers
   - Client-side: Parse SSE events with proper buffering
   - Handle connection errors and timeouts
   - Support abort/cancel operations

6. **Graceful Degradation**:
   - Check for missing DIFY_API_KEY at page load
   - Show clear setup instructions when not configured
   - Don't crash or show cryptic errors
   - Provide link to documentation

7. **Testing Approach**:
   - Unit tests: Component behavior and logic
   - E2E tests: User flows (already exist from Story 10.1)
   - Manual testing: Both configured and unconfigured states
